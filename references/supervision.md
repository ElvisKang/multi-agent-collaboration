# 监督提醒与管理者判断

监督者观察开发者和需求管理者的工作，掌握的信息可能不完整。提醒是需要判断的线索，不是已确认故障、用户决定或新的执行授权。仅在发现/收到异常提醒时读取本页，正常研发不增加汇报步骤。

## 监督者如何提醒

- 单需求进度异常、需解释当前等待或执行状态时，可直接联系所属需求管理者；跨需求影响、需求管理者本身失效、提醒后仍无合理处理或重大协作安全风险时，可联系核心。按影响和可达性选择，不必逐级等待或同时广播两者。
- 消息简明区分已观察事实、观察时间/来源、怀疑及不确定处，说明希望管理者核实的问题。例如“该任务登记进行中，近一段时间未见新增结果；可能仍在等待构建，请核实原操作是否活动”，而非直接断言停工或要求换人。
- 无新证据不重复提醒或多路催促。紧急风险或影响扩大时可以升级，关联原提醒并说明增量。用户明确要求的监测频率和转达任务继续遵守。

## 任一管理者收到后

1. 明确被观察的任务、工作包、会话和时间范围，区分监督者观察、推断与明确转达的用户指令。即使来自监督者，也不能默认已充分了解工作细节。
2. 按提醒涉及的问题核对最小必要现场：当前任务和下一动作、原操作及实际回合、产物增量、已知等待/阻塞。需要时询问负责执行的管理者；核心只核对该异常，不接管整套技术审核。对被质疑的自身调度同样基于实际证据判断，不只复述旧登记。
3. 给出结论：异常成立、属于正常执行/合理等待，或证据不足。说明关键依据与下一动作；证据不足时指出待确认项及跟进者，不凭提醒直接取消、重派、改 Owner 或新建冲突 writer。
4. 异常成立时在自身权限内处理；更高层协调或用户决定分别按原边界升级。明确用户紧急停止指令按实际授权执行，不能借“先核实”拖延。
5. 向提醒者简短返回判断和处理结果；不是纯 ACK，不重复全部日志。相同提醒已处理且无新信息时不循环往返。只有未决异常、任务状态或项目影响需要保留时更新对应当前交接，误报和普通解释不永久沉淀为事故或新增规则。

管理者不能因监督者可能误判就忽略提醒，也不能把它当无需判断的权威。处理闭环的目标是依据现场恢复/确认正常推进，不是证明某个角色判断更强。
