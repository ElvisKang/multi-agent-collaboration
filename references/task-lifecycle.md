# 需求生命周期与标准术语

仅在定义任务边界、阶段转换或停点含义不明确时读取。术语用于清楚表达，不要求每条消息填写完整状态表；项目既有状态枚举继续沿用。

## 表述先说明范围

需求是用户要验收的完整目标；阶段是管理者拆出的推进步骤；工作包是派发给某个执行者的有界实现。工具调用和会话是执行载体，其结束不等于工作包或需求完成。

每次关键转换写清“任务/阶段或工作包、当前版本、转换结论、下一责任人和动作”。一句话或当前交接中的已有字段足够，不新增一套登记。

## 正常推进

| 术语 | 标识 | 成立条件与下一责任 |
|---|---|---|
| 需求立项 | REGISTER | 核心登记目标、需求管理者和整体验收条件；需求管理者开始澄清与拆解 |
| 任务派发 | ASSIGN | 管理者给具体执行者明确工作包、输入、范围、验收和权限；执行者承接或报告关键缺口 |
| 任务承接 | ACCEPT | 执行者理解范围并负责实施，可从实际开工确认，无需另发收件 ACK |
| 实现与自验 | IMPLEMENT | 执行者完成实现，验证实际代码与必要集成边界，准备交付 |
| 冻结待审 | SUBMIT | 相关执行者结束该范围的修改，固定版本并送审；管理者接续审核 |
| 审核需改 | REQUEST_CHANGES | 管理者集中给出具体失败条件、影响和修复验收；开发者修复或由管理者接手 |
| 审核通过 | APPROVE | 当前工作包符合审核条件；管理者立即判断并启动下一项已授权工作 |
| 集成验证 | VERIFY | 管理者对组合成果组织约定验证，例如构建、资源检查、烧录和设备验收；按实际结果处理缺口 |
| 需求验收通过 | ACCEPT_TASK | 需求管理者依据全部整体验收条件和约定的用户确认认定满足；未验项须如实处置，进入收尾 |
| 任务关闭 | CLOSE | 更新任务完成状态、长期结论、证据及临时资源归属；整项需求结束 |

修复后重新自验、冻结待审，沿用原任务和问题记录。审核通过仅针对所述工作包；单阶段通过不代表整项需求验收通过。小任务可以合并相邻步骤，无需为了术语额外派发、审批或扩展测试。

## “停写”的两个明确替代

- **冻结待审**：保持指定文件范围和版本供审核；执行者不自行进入未派发阶段，管理者仍继续审核与续派。
- **移交写入权**：安排替换者先明确通知旧执行者撤任并确认职责释放（自主接力由旧方主动交出），核对旧 writer 及相关后代结束相应写入，再登记并授权新 writer；任务继续，由新 writer 承担下一动作。CLI 调用结束不等于职责解除。

停止写入是以上动作的具体条件，不单独作为任务状态或交付结论。写“已停止修改 M1 的 v2，冻结待审，由管理者复审”，或“将 M2 写入权由 A 移交 B”；避免只说“已停写”。

冻结后确需编辑时，由管理者安排修复或明确重新开放该范围，声明旧快照失效；编辑、自验后生成新版本。冻结仅限实际审核范围；隔离且独立授权的其他工作可以继续。

## 等待、暂停与接力

| 术语 | 标识 | 含义与恢复责任 |
|---|---|---|
| 等待结果 | WAIT_RESULT | 原操作在执行或结果未知；记录操作 ID、跟进者、结果获取方式和恢复触发，跟随原操作而非重派 |
| 待用户决策 | WAIT_DECISION | 已提出具体问题，注明影响和答复入口；对应管理者接收答复后继续，独立授权工作可并行推进 |
| 执行阻塞 | BLOCKED | 缺必要输入、权限或能力；写原因、解除条件及负责处理者，管理者判断替代路径 |
| 任务暂停 | PAUSE | 用户或权限范围内的管理者明确暂停指定范围；注明来源、原因、恢复条件及负责人，阶段完成不会自动触发暂停 |
| 会话接力 | RELAY | 更换承载会话，保留任务、成果、失败问题及未决执行，按接力规则更新席位并通知；需求并未结束 |
| 任务取消 | CANCEL_TASK | 用户或有权管理者明确终止指定任务，处理在途操作与成果；取消一次工具调用不等于取消任务 |

等待必须有可执行的恢复安排，例如原调用有界等待、事件回调或已确认的观察者通知。需要外部触发而当前没有接收机制时，如实登记阻塞，交管理者安排；不能把“任务未完成，等待继续”当有效等待，也不例行新建自动化。

已获得的条件授权在条件满足时执行，不再询问同一授权；条件尚未满足时继续完成已授权前置工作。确有权限缺口则明确提出，不把阶段拆分本身变成逐阶段人工批准。

## 管理者的推进闭环

审核或验证结束后，管理者必须选择并执行下一项已授权动作，或登记上述明确的等待、阻塞、暂停、取消或关闭。阶段汇报是通知事件，不是任务终点；开发者冻结待审也不是管理者暂停的指令。

阶段通过 → 下一工作包输入与权限齐备 → 直接续派或亲自执行。真正缺输入或权限 → 登记缺口并推进不受影响的部分。用户要求只做某阶段时，按该真实范围收尾，不借持续推进扩大需求。

完整菜单示例：M1 派发 → 实现自验 → 冻结待审 → 审核需改 → 修复送审 → 审核通过 → 管理者派发 M2 → 后续阶段 → 集成验证 → 需求验收通过 → 关闭。M1 的“不自行进入 M2”只约束该工作包执行者，不解除管理者续派责任。

## 与现有记录的关系

TASKS 保留 TODO / IN_PROGRESS / REVIEW / BLOCKED / DONE，不新增全部动作枚举。工作包冻结待审对应其 REVIEW，父需求仍可 IN_PROGRESS；整体验收和收尾完成才把父需求置 DONE。待决/暂停/取消等按项目既有机制在当前交接注明，避免误标 DONE。sessions 的 ACTIVE/UNRESOLVED/ENDED 仅描述会话绑定，不是任务状态。

核心和监督者发现“进行中、没有执行者或下一动作、也没有明确等待/阻塞/暂停”时，将其视为推进缺口，核对后由有权管理者恢复调度；监督者不直接接管。术语不改变既有工具权限或实际唤醒能力。
