# 任务推进、登记与接力

存储位置由项目规范决定。模板：[任务表](../assets/tasks-template.md)、[当前交接](../assets/handoff-template.md)、[会话快照](../assets/sessions-template.md)。

## 任务与唯一写入

- 新需求在核心登记，绑定一个子管理席位；分解出的独立并行工作可登记子任务及父任务。实现、review、修复、换会话沿用对应任务 ID，不重复开修复任务。
- ID 遵循项目规则；未定义时用项目名-YYYYMMDD-NNN，序号包含已完成记录参与查重。已有相同需求/worktree 绑定先复用，不把无关新需求误接到已完成任务。
- 任务表分别记录管理席位与当前实际写入 Owner。角色不授予写权限；没有开发者时管理者可以是 Owner。共享 worktree 同时只有一个实际 writer，真正并行编码使用已授权隔离目录和有界子任务。
- 主工作区为唯一本地登记入口，先规范化真实路径；登记不会切换工具执行目录。写前重读，保留其他任务与会话变化，约定串行修改；文件约定不等于已经有强制锁。
- 核心维护需求管理分配，子管理者维护所属任务与新开发者加入；登记串行但不默认由核心代写每个执行状态。项目明确另有写入归属时遵循它，只发送最小必要登记变更，不附研发流水；每个角色可更新自身接力后的同一席位与对应 Owner，通知直属管理者/相关参与者，无需等上级批准。修改前确认自己仍为当前有效负责人，旧会话不得凭旧上下文恢复登记。
- 扩大范围前更新任务；只有用途而无具体需求时记 TODO，不自动开发。纯只读或文档操作不要求为每个动作建立研发任务。

## 推进与决策

以可验收功能切片推进，尽早在授权范围内检查真实集成、构建与资源限制。任务先通过一个真实闭环，再扩大范围；不以半成品数量或测试数量代替交付。

阶段动作及等待/暂停的具体含义见 [生命周期](task-lifecycle.md)。阶段通过后管理者续派下一项已授权工作；冻结待审不等于整项暂停。任务状态沿用 TODO、IN_PROGRESS、REVIEW、BLOCKED、DONE；DONE 须满足实际验收条件。BLOCKED 写明原因、解除条件及可继续工作。等待用户、设备或外部输入时不伪造推进，不循环催促；其他独立且已授权的工作可以继续。

需要用户决定的问题放当前任务交接，并由需求管理者在 App 直接提出。监督者可通知用户并转达，原问题解决后原位更新，不复制问答历史。核心只接收阻塞及依赖影响，不承担该问答中转。

## 每份资料只承担一种职责

| 资料 | 内容 |
|---|---|
| TASKS | 任务目标、父任务、管理席位、当前写入 Owner、状态、目录、范围、验收、依赖与当前交接 |
| sessions | 逻辑席位与真实会话、上下级关系及路由；字段见会话快照 |
| 当前任务交接 | 当前版本/成果、有效授权、执行者和在途操作、未决问题、必要证据、下一动作 |
| 核心当前交接 | 各需求入口、阶段与依赖、阻塞、待处理管理异常；引用 TASKS，不重复负责人表和全部开发细节 |
| 原始证据/投递记录 | 必要日志、固定版本、操作标识及防重复投递记录；不复制到 sessions |

跨层汇报按角色职责筛选；普通研发事件保留在需求交接，只有需核心行动或改变项目安排的重要增量才通知核心。核心摘要引用任务入口，不复制审核轮次、执行号、SHA 或技术排障过程。

更新交接时替换已失效的当前说明，不在文件顶部持续叠加“最新状态”。保留会影响下一步决策的事实；长期结论另写总 HANDOFF/知识库，不完整备份旧流水账。

## 压缩还是新会话

- 目标和执行稳定、仅历史变长：精简当前状态，利用可用的压缩能力。
- 阶段完成、历史污染、持续遗忘或无增量循环：整理当前交接后评估干净会话接力。
- 连续客户端报错：核对真实执行和身份后接力；fork 可用于抢救摘要，但不默认继承整段历史或认为 fork 已解决客户端故障。
- 不按固定小时数/消息条数强制轮换，不虚构上下文用量。核心、子管理者、开发者都可接力；角色唯一性不等于会话永久不变。

## 执行者替换：先撤任再授权

此流程适用于管理者安排换人，也适用于角色自行创建继任者。多个开发者并存不是问题；管理者指定同一工作包唯一执行时，必须维护该归属的启动与终止，而非仅维护会话数量。

1. **通知撤任**：由安排替换者联系旧会话的真实 ID，明确不再负责哪个工作包、停止哪些写入/派生，并要求保留成果、列出在途操作和子执行者。不要用普通技能更新、CLI 中断或仅改登记替代通知。
2. **确认释放**：取得旧执行者对该范围撤任的确认，结合真实执行状态核对相关回合、子执行者和未决操作均已结束写入。普通退任确认不能代替实际执行证据，单次 CLI 退出也不能代替撤任确认；确认针对本次范围和时点。
3. **移交职责**：整理当前版本和未决事项，串行更新工作包/Owner 与席位。工作包撤任不等于整名开发者结束，它仍可承担另外已明确分配的独立任务。
4. **授权继任**：明确把该工作包和写入范围交给新会话，然后开始实现。候选可提前只读准备，但此前不授予冲突职责。
5. **保持退任**：旧会话收到通知、技能更新或普通唤醒消息时，只处理通知本身；恢复旧工作须有新派发并取得相应归属。管理者发现任何入口又激活旧工作，先收回冲突执行并核对版本，不能继续使用之前的“已停”结论。

旧会话失联时写清接管阻塞；若运行环境能真正撤销其写入能力，可先实施隔离并核对未决执行，再由有权管理者决定接管，记录缺少旧方确认的事实。没有停止证据或隔离能力时，继任只读或处理独立隔离工作。角色自行接力可由旧会话主动结束其职责并交出证据，无需向自己发送撤任消息，但不能省略释放与继任授权边界。

## 接管顺序

1. 当前负责人更新精简交接：目标和边界、真实版本、当前成果、未决执行及操作 ID、必要授权、阻塞、证据和唯一下一动作。
2. 当前角色可自行创建自己的候选接力会话；上级也可在已有授权内安排替换，用户手动创建的会话可接纳。候选读取 skill、项目约束和当前交接，自行核对真实 sessionId；首次打印基础信息，不自动开工争写。
3. 按上方执行者替换流程明确旧方职责结束：安排者通知撤任，或旧方在自主接力时主动交出职责；取得释放依据后再跟踪确认相关 writer 及其后代结束指定范围写入。cancel 请求、文件短时不变、SHA 一致或旧自报均不能单独代替停止证据。
4. 新会话确认接单后，由当前角色或有权安排替换的管理者串行更新同一席位绑定及对应任务 Owner，通知相关方，不将登记通知变成上级审批。保留直接 previous_session_id，按实际新 ID 重置路由证据；通知受影响参与者只需说明席位已切换并给当前资料入口。
5. 旧会话停止派发、写入和同任务管理；迟到消息由新负责人按版本与执行记录判定，不自动触发重派。失败计数、未决操作、范围和授权边界不随迁移清空。

普通子管理接力不必停止任务内所有独立执行；但未决操作必须完整移交，待改动/写入权不能重叠。若不能确认旧 writer 已结束相关写入，新会话只读诊断或处理隔离工作，不启动冲突实现。

核心正常接力先准备项目当前摘要及候选核心，旧核心停止创建/分配后再切换 core_manager 指针，不能同时运行两个有效核心。核心失联时监督者升级用户，不自行提升为核心。登记已变但旧会话又收到消息时，先读当前席位，不能重夺管理权。

## 收尾

review 与修复沿用同一任务；验证证据对应最终版本。更新任务与必要会话状态，长期结论进入共享资料；已结束且无依赖的会话和临时文件可清理，保留任务 ID 与必要证据。跨机器重建本机路由，不直接使用复制来的 ACTIVE 状态。
